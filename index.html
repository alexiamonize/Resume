The Five Chairs
  • Chief Executive. Cannot delegate the budget or the narrative. Hears about it first from a customer questionnaire or a board member forwarding an article, and gets asked whether it can wait two years
  • Chief Financial Officer. Meets it as a multi-year cost that is in no plan yet and cannot be sized until the inventory exists. Engages at one gate, the budget, which is where the leverage sits
  • Business or data owner. Holds the one answer nobody else can supply: how long the information must stay confidential, which is a different clock from how long it must be retained
  • Chief Information Security Officer. Owns the outcome without the capacity. Gets asked what percentage is done when there is no denominator, because the inventory is the business case rather than a precondition for it
  • Chief Technology Officer. Learns that size is what breaks systems, that following the standard is not a complete instruction when authorities disagree, and that part of the estate will not migrate at all
How It Was Built
  • Structured around evidence about why these briefings fail. Escalating the threat narrative reduces engagement rather than increasing it. The programme closes psychological distance instead of raising volume, drawing on construal-level theory to explain why a subject that is years away, nowhere in particular, hypothetical, and happening to other people resists being acted on
  • Wrote four discussion exercises that produce a finding rather than a quiz score, including a completeness test against the thirteen migration use cases where the items an organisation cannot answer are themselves the result
  • Treated the destination as still moving. Two signature standards remain unfinished and Merkle Tree Certificates are a draft, so the programme argues for building systems where cryptography can be changed rather than for any single migration
  • Kept credentialing alongside the engagement, working from the published standards rather than summaries of them and taking further cryptography coursework as the implementation guidance continues to be written

Judgment Under Production Conditions
  • Found a quality gate that ran but never actually gated. The anti-fabrication QA check computed a ship/no-ship verdict on every account report, but the persistence layer wrote the report to the database regardless of the result. A blocked report reached the database identically to a clean one. Located the missing conditional, cited the line, and specified the fix before it reached a salesperson's screen.
  • Caught the system inventing freshness and certainty it didn't have. Buying-signal timestamps were being stamped with request time instead of the actual observation date, making a 19-month-old funding round read as "today." Source URLs were being discarded and replaced with empty strings. Per-signal and per-contact confidence scores were hardcoded to a flat default, erasing the real distinction between a verified decision-maker and an unconfirmed name.
  • One funding event, two cards, double-counted. A regex truncation bug split a single event into two buying-signal cards, which then scored into both the Timing and Budget dimensions of the same account. One data point became two independent reasons to prioritize it.
  • Every defect above was confirmed against live API responses and database rows, not read off the code. Each fix brief cites the file, the line number, and a query that reproduces it.
